# タスク依存関係ガイド

> **Version**: 1.0.0
> **Last Updated**: 2026-02-06
> **Author**: 足軽8号（別働隊・ビルド確認担当）

## 概要

マルチエージェント並列開発において、タスク間の依存関係を正しく管理することは極めて重要である。
依存関係を無視した並列作業は、ビルドエラー、型エラー、ファイル競合を引き起こす。

本ガイドでは、依存関係の定義方法と並行作業時の注意点を解説する。

---

## 1. blockedBy / blocks の使い方

### 基本概念

| フィールド | 意味 | 使用例 |
|------------|------|--------|
| `blockedBy` | このタスクが開始できない理由（先行タスク） | 型定義が完了しないと実装できない |
| `blocks` | このタスクが完了しないと開始できないタスク（後続タスク） | 型定義完了で実装タスクが開始可能に |

### YAML記述例

```yaml
# タスクA: 型定義（先行タスク）
task:
  task_id: task_001_type_definition
  blocks:
    - task_002_component  # このタスクが完了するとtask_002が開始可能

# タスクB: コンポーネント実装（後続タスク）
task:
  task_id: task_002_component
  blockedBy:
    - task_001_type_definition  # task_001が完了するまで開始不可
```

### 依存関係の方向

```
先行タスク (blocks) ──────▶ 後続タスク (blockedBy)
     │                            │
     │  「私が完了しないと       │  「あれが完了しないと
     │   次が始められない」       │   私は始められない」
     └────────────────────────────┘
```

## 2. 並行作業時の注意点

### 2.1 順序を守るべきパターン

| 先行タスク | 後続タスク | 理由 |
|------------|------------|------|
| 型定義（types/*.ts） | コンポーネント実装 | 型がないとimportエラー |
| Entity定義 | Service実装 | Entityがないと依存注入エラー |
| 共通コンポーネント | ページ実装 | 共通部品がないとビルドエラー |
| API設計 | FE/BE実装 | エンドポイントが未定だと実装不可 |
| DB設計 | Seed作成 | テーブル構造がないとSeed作成不可 |

### 2.2 絶対禁止事項

```
██████████████████████████████████████████████████████████████████████████
█ 【禁止】同一ファイルの同時編集（RACE-001）                             █
██████████████████████████████████████████████████████████████████████████
```

複数の足軽が同一ファイルを同時編集すると、後から保存した方が先の変更を上書きしてしまう。

**対策**:
- タスク割当時にファイル担当を明確化
- 同一ファイルを編集するタスクは `blockedBy` で直列化
- 競合リスクがある場合は `status: blocked` で報告

### 2.3 並列可能なパターン

| タスクA | タスクB | 並列可能な理由 |
|---------|---------|----------------|
| FE実装 | BE実装 | 別ディレクトリで独立 |
| 画面A実装 | 画面B実装 | 共通コンポーネント完了後なら可 |
| Seed A | Seed B | 異なるテーブルなら可 |

## 3. 依存グラフの例

### 3.1 基本パターン（直列）

```
[型定義] ──blockedBy──▶ [コンポーネント] ──blockedBy──▶ [ページ実装]
```

### 3.2 分岐パターン（並列可能）

```
                    ┌──blockedBy──▶ [FEコンポーネント] ──┐
[API設計] ──────────┤                                    ├──▶ [結合テスト]
                    └──blockedBy──▶ [BEサービス] ────────┘
```

### 3.3 複合パターン（実際の開発）

```
[DB設計]
    │
    ├──blockedBy──▶ [Entity定義] ──blockedBy──▶ [Service実装]
    │                                                │
    └──blockedBy──▶ [型定義(FE)] ──blockedBy──▶ [コンポーネント]
                                                     │
                                    ┌────────────────┘
                                    ▼
                              [ページ実装] ◀──blockedBy── [Service実装]
                                    │
                                    ▼
                              [ビルド確認]
```

## 4. 足軽の声（実体験に基づく教訓）

### 4.1 時間短縮に効果的だったこと

> 「変換対象リストがあると時間短縮になる」

- 修正対象ファイルが事前にリストアップされていると、調査時間が削減される
- 特にFE-BE整合性チェックでは、対象ファイル一覧が重要

### 4.2 重複作業を防止した工夫

> 「bugs.yamlに実装ステータス反映で重複作業防止」

- バグ修正時、誰が対応中かを明記することで重複を防止
- `status: in_progress / assigned_to: ashigaru5` のような記載

### 4.3 可視化の重要性

> 「進捗共有ファイルで可視化」

- 足軽間で作業状況が見えないと、待機時間の見積もりが困難
- `queue/progress.yaml` のような進捗共有ファイルがあると効率的

### 4.4 ビルド確認担当からの教訓

- **モジュール追加時**: 他の足軽がモジュール作成完了後でないとapp.module.ts更新不可
- **型エラー**: 型定義が先行しないと、後続のコンポーネント実装でエラー多発
- **apiClient共通化**: 全サービスが共通クライアントを使用することで整合性向上

## 5. 依存関係管理のベストプラクティス

### 5.1 タスク作成時

1. 先行タスクを明確にする（`blockedBy` を必ず記載）
2. 後続タスクへの影響を考慮する（`blocks` を記載）
3. ファイル担当を明確化し、競合を防止

### 5.2 タスク実行時

1. `blockedBy` のタスクが全て完了しているか確認
2. 同一ファイルを他の足軽が編集中でないか確認
3. 完了時は `blocks` のタスクに通知

### 5.3 軍師・家老の責務

1. 依存関係を考慮したタスク割当
2. 循環依存の回避（A→B→A はNG）
3. クリティカルパスの特定と優先順位付け

## 6. チェックリスト

### タスク開始前

```
□ blockedBy のタスクは全て完了しているか
□ 同一ファイルを他の足軽が編集中でないか
□ 必要な型定義・Entity・共通コンポーネントは存在するか
```

### タスク完了後

```
□ blocks のタスクに完了を通知したか
□ 後続タスクの blockedBy を解除可能か確認したか
□ ビルド確認を依頼したか（大きな変更の場合）
```
