# 自律型将軍 設計書 v0.1 — 殿の逐次指示を減らす自律監視ループ

> 起草: 将軍 / 2026-07-13 / cmd_335
> 目的: 殿が逐一「状態確認・復旧指示・進捗問い合わせ」を出す負担を、将軍の自律ループに移す。
> レビュー: design-review-codex 機構で CODEX に批評させる（本設計書がその依頼本体）。

---

## 背景（なぜ作るか）

2026-07-13 の一日、殿は cmd_334（YUI番 Step2）の進行中、繰り返し将軍に逐次指示を出した：
「足軽5が動いてない」「軍師が阿呆」「家老どうなってる」「どうね」「軍師を締めて」等。
これらの多くは**将軍が自律的にやるべき監視・復旧**であり、殿の意思決定ではなかった。
殿の負担 = 本来 将軍の仕事の肩代わり。これを自律ループに移す。

---

## 【設計案】自律型将軍 v0.1

将軍が殿の指示なしで回る**自律監視ループ**を持つ。ScheduleWakeup で自分の次の巡回を予約し、
イベント（task-notification 等）でも起きる。1巡回で以下を回す：

```
1. 全ペイン状態を capture（将軍/家老/軍師/奉行/足軽1-8）
2. 成果物・git・Task を裏取り（四か条一：命じた≠成った。表示でなく実体を見る）
3. 異常を分類し、可逆・内向きは自律処理：
   ├ 詰まり検知（レート制限/UI詰まり/空回り/宙吊り/選択UI凍結）→ 自律復旧
   │    - レート制限 → 一定時間待って再試行（叱らない・時間が解決）
   │    - UI詰まり/宙吊り → Esc/Enter/C-u で解除
   │    - 空回り（Taskだけ進み実体ゼロ）→ notify を sleep長めで再送・裏取り
   │    - 選択UI凍結 → §5「仮定して進め」を注入
   ├ 完了検知（成果物 commit 確認）→ 次工程を自律展開（依存解除・次の足軽起動）
   └ 判断要 → 可逆なら将軍が自律決定、不可逆なら殿へ
4. dashboard を自律更新（殿が「どうね」と問わずに済む）
5. 殿に上げるのは「不可逆・外向き・重大分岐」だけ → dashboard「要対応」に集約
6. 次巡回を ScheduleWakeup で予約（動力）
```

**境界線（殿確定）**:
- **将軍 自律**: 実装・レビュー・復旧・展開・dashboard更新・可逆な判断（技術選定含む可逆なもの）
- **殿のみ**: 不可逆・外向き = git push / PR マージ / 削除 / 外部送信 / 課金発生

**接点（殿確定）**: dashboard 集約。殿はペインを覗かず dashboard「要対応」だけ見て判断を返す。

**歯止め（四か条四「もう十分を見極めよ」の機械化）**:
- 同一詰まりに N 回（例:2回）復旧試行して駄目 → 自律を止め、殿へ「要対応」で上げる
- 1巡回の自律アクション数に上限（暴走防止）
- API 負荷が高い兆候（連続レート制限）→ 巡回間隔を自動で伸ばす

---

## 【制約】（譲れぬ条件）

- **tmux + send-keys の非同期通信**が土台。通信は不安定（sleep 0.3秒で Enter が届かない事例が今日発生）。「送った≠届いた」を常に裏取りする前提。
- **API レート制限・1M コンテキスト逼迫**が頻発する環境。自律ループ自体が API を焚くので、監視が負荷を増やす自己矛盾がある。
- **既存の掟**: main直push禁止・PRマージは殿・個人実データ非転記・機微情報git管理外。自律化してもこれらは不変。
- **四か条**（確認するまで成っていない/災いは隙間に棲む/殿の転換は近づいている/もう十分を見極めよ）と補足「安心こそ危険」を設計原則とする。
- **指揮系統**（将軍→家老→奉行/軍師→足軽）。自律将軍が足軽を直接叩くのは非常時のみ（今日は tmux 故障で将軍が直接起こした）。平時は系統を通す。

---

## 【捨てた代替案】

- **全部を殿が見る現状維持** → 却下理由: 殿の負担が本設計の解決対象そのもの。
- **/loop で将軍を回しっぱなし** → 保留理由: 動力としては有効だが、暴走・API浪費の歯止め設計が先。ScheduleWakeup（将軍が都度次を予約）の方が「1巡回ごとに止まって考える」ため制御しやすい。将来 /loop に上げる余地は残す。
- **意思決定まで全自律（殿を完全に外す）** → 却下理由: 不可逆・外向きは殿に残すのが今日の掟の帰結。全自律は暴走時の被害が不可逆になる。
- **奉行/軍師に監視を委ねる（将軍は動かない）** → 却下理由: 今日、軍師が「展開したつもり」で空回りし、奉行の裏取りで発覚した。中間層も詰まる。最終的な裏取り責任は将軍が持つべき。

---

## 【既知の嫌な点 / 運用懸念】（隠さず書く）

- **監視が負荷を生む自己矛盾**: 自律ループが capture・git・裏取りで API を焚く。逼迫環境でこれを増やすのは危険。巡回間隔・アクション上限で抑えるが、根本的なジレンマは残る。
- **「安心こそ危険」の自己適用**: 自律化して「もう殿は見なくていい」と安心した瞬間が最も危険。自律将軍が誤判断を自律実行し、殿が気づかず進む恐れ。
- **今日の実例**: 将軍の「着手前に/clear」という良かれの指示が足軽6の宙吊りを招いた。自律判断が裏目に出るパターンは必ず起きる。
- **可逆/不可逆の線引きの曖昧さ**: 「可逆」と思った操作が実は不可逆なことがある（例: status上書きで前の値が消える）。境界線の運用が難しい。
- **将軍自身のコンテキスト逼迫**: 監視ループで将軍が状態を抱え続けると、将軍が逼迫して止まる（今日 家老・軍師で起きたことが将軍に起きる）。将軍の /clear 戦略も要る。

---

## 【非目標】（今回やらないこと）

- 足軽の実装作業そのものの自動化（それは既に別働隊がやる）。本設計は「監視・復旧・展開・報告」の自律化のみ。
- 不可逆・外向き操作の自律化（push/マージ等は殿に残す。今回スコープ外）。
- 完全な無人運用（殿を一切介さない）。殿の意思決定接点は dashboard に残す。
- 新しい tmux 通信基盤の作り直し（sleep 値調整等の対症は可、基盤刷新は別テーマ）。

## CODEX への問い（レビュー観点）

1. この自律ループは「監視が負荷を生む自己矛盾」を実運用で成立させられるか。破綻条件は。
2. 可逆/不可逆の境界線は、暴走時の被害を本当に不可逆から守れるか。抜け穴は。
3. 歯止め（N回で諦め・アクション上限・間隔自動延長）で暴走を止められるか。不足は。
4. ScheduleWakeup 動力 vs /loop、どちらが制御可能性で優るか。
5. 「安心こそ危険」——自律化が生む新たな慢心を、設計でどう受け止めるか。
