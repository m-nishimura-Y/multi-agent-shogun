# 自律型将軍 設計書 v0.2 — 封じ込め主体への転換

> 起草: 将軍 / 2026-07-14 / cmd_335
> 前版: [v0.1](autonomous_shogun_design_v0.1.md)（復旧主体）
> レビュー: [議事録第2号](design_review_002_autonomous_shogun.md)（CODEX gpt-5.4）
> **転換の核**: v0.1「自律＝将軍が代わりに全部やる（復旧主体）」→ v0.2「自律＝暴走の封じ込めと怪しい箇所の厳格確認に絞る（封じ込め主体）」

---

## なぜ転換したか（CODEX 指摘の帰結）

v0.1 は殿の負担を将軍に移すだけで、**将軍が新たな単一障害点**になる（C1）。今日 家老も軍師も詰まった。将軍だけ詰まらぬ保証はない。ゆえに将軍は「全部を自動で前進させる」のでなく、**止めるべきを止め、確かめるべきを確かめ、上げるべきを上げる**に徹する。

---

## 設計原則（v0.2 の背骨・CODEX最小対案）

```
原則1: 前進より封じ込め。「これ以上広げない」を「勝手に進める」より優先する。
原則2: UI操作は原則危険寄り。Esc/Enter/仮定注入は自律の標準手段から外す。
原則3: 完了は単一シグナルで判定しない。最低2系統一致まで前進しない。
原則4: dashboardは進捗面でなく「不確実性の露出面」。正常らしさより未確認印を残す。
原則5: 怪しいものだけ厳しく見る。全ペイン常時監督はしない。
原則6: 監視が苦しいほど監視を減らす（縮退）。負荷の正フィードバックを断つ。
```

---

## 真実源の優先順位（未解決論点C→確定）

「何を真実とみなすか」を固定する。上ほど強い：

```
1. ファイル実体・git（実ホストの副作用）      ← 最も信用する
2. 成果物の中身検証（commitされた≠正しい）
3. Task 状態（親が更新する宣言・ズレる前提）
4. tmux 表示（capture）                        ← 参考。単独で真実にしない
5. エージェントの自己申告（「やった」）        ← 最も疑う。必ず1で裏取り
```

**rule**: 4や5が「完了」と言っても、1で裏が取れるまで「未確認」印を dashboard に残す。

---

## 完了判定（原則3・C3対処）

工程完了は次の**2系統以上の一致**を要する（単一commitで通さない）：

```
系統A（実体）: 期待ファイルが存在し中身が仕様を満たす（空/TODOだけは不可）
系統B（履歴）: commit されている、正しいブランチ、意図した差分
系統C（宣言）: 足軽/親が done を上申（notify到達を裏取り）

→ A+B 一致で「実装完了」。Cだけ、Bだけ、では「未確認」。
```

## 自律ループ v0.2（封じ込め版）

```
【将軍 封じ込めループ】未解決異常があるときだけ再起床（定時巡回を減らす・C5/C6）
  巡回には世代番号を付す。古い巡回結果は破棄（重複起床・上書き防止・C6）。

  1. トリアージ（全監督でなく、前回「怪しい」と印した対象＋新規イベントだけ見る）
  2. 各対象を真実源優先順位で裏取り（実体>git>Task>表示>自己申告）
  3. 分類：
     ├ 【封じ込め対象】暴走・誤進行・文脈破壊の兆候
     │    → まず止める（次工程展開を保留）。広げない。dashboardに「隔離」印。
     ├ 【厳格確認対象】完了を主張するが未裏取り
     │    → 2系統一致を確認。不一致なら「未確認」印で保留、殿に上げるか判断
     ├ 【単純詰まり】レート制限＝待つ / 明白なUI宙吊り＝1回だけ慎重に解除
     │    （UI操作は危険寄り。2回目は自律せず殿へ・C2）
     └ 【正常完了・2系統一致】→ 次工程を展開（可逆な範囲のみ）
  4. dashboard更新：進捗でなく「確実/未確認/隔離/競合/殿判断待ち」を露出
  5. 殿へ上げる（下記トリガー）
  6. 未解決異常が残れば次巡回を予約。無ければループ停止（負荷ゼロに戻る）
```

---

## 殿へ上げるトリガー（報告遅延の許容幅・未解決論点→確定）

「不可逆・外向きだけ殿へ」では遅延が既成事実化する（CODEX指摘）。ゆえに拡張：

```
即上げる（可逆でも）:
  - 同一異常に自律復旧 2回失敗 → 止めて殿へ（四か条四の機械化）
  - 完了判定が系統間で矛盾（表示done・実体なし等）
  - 将軍自身の逼迫兆候（自己コンテキスト X≥閾値）→ フェイルセーフ（下記）
  - 不可逆・外向き（push/マージ/削除/外部送信/課金）
  - 30分以上どの工程も前進していない（静かな劣化の検知）
```

---

## 将軍フェイルセーフ（単一障害点対策・C1）

将軍自身が詰まる/逼迫する場合の露出策：

```
- 将軍は巡回ごとに status/shogun_heartbeat.yaml に「最終巡回時刻＋世代」を書く。
- 将軍が数値トリップワイヤー（X≥閾値）に達したら、巡回を止め、
  dashboardに「将軍逼迫・要殿確認」を出してから /clear（自己の永続化後）。
- heartbeat が一定時間更新されない＝将軍停止。これを殿が dashboard で気づける形にする。
  （将来: 家老or別プロセスが heartbeat 鮮度を監視し殿に露出。今は殿が随時確認）
```

---

## 監視縮退（負荷の正フィードバック遮断・C5）

```
- 連続レート制限を検知したら巡回間隔を自動延長（例: 90s→270s→1200s）。
- 1巡回のcapture対象を「怪しい印がついたペインのみ」に絞る（全8足軽を毎回見ない）。
- 異常ゼロが続けばループ停止（ScheduleWakeup予約しない＝完全に負荷ゼロ）。
```

---

## 境界線（殿確定・不変）

- **将軍 自律**: 封じ込め・厳格確認・可逆な次工程展開・dashboard更新・可逆判断
- **殿のみ**: 不可逆・外向き（push/マージ/削除/外部送信/課金）＋自律2回失敗の判断

---

## 残る未解決論点（v0.3 or 実装時に詰める）

- 「怪しい」の観測可能な判定基準（空回り/宙吊り/凍結を機械判定に落とす具体ルール）
- heartbeat 鮮度を誰が監視するか（将軍停止時の最終フェイルセーフの担い手）
- 「仕様を満たす中身」の検証をどこまで自動化するか（系統Aの厳密度）
- 動力: ScheduleWakeup単発予約で足りるか、将来 /loop に上げるか

## v0.2 で変わったこと（1行）

**「将軍が代わりに全部やる」を捨て、「暴走を封じ込め・怪しいものだけ厳格確認し・止めるべきを止めて殿に上げる」に絞った。将軍を万能の復旧者でなく、規律ある門番にした。**
