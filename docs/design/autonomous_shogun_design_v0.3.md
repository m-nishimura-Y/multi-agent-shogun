# 自律型将軍 設計書 v0.3 — 現行統治に従う封じ込め主体

> 起草: 将軍 / 2026-07-14 / cmd_335
> 前版: [v0.2](autonomous_shogun_design_v0.2.md)（封じ込め主体・統治と衝突）
> レビュー: [議事録第3号](design_review_003_autonomous_shogun_v0.2.md)（CODEX 第2撃）
> **v0.3の核**: v0.2は既存統治（dashboard=家老責任/Linear=正本/ポーリング禁止）と衝突した。殿裁可により**自律将軍を現行統治に合わせる**。設計側を曲げて二重権威化を防ぐ。

---

## 統治整合（殿裁可・D6対処・最優先の前提）

自律将軍は既存の掟を**上書きせず従う**：

| 既存の掟 | v0.2 の違反 | v0.3 の是正 |
|---------|-----------|-----------|
| **dashboard は家老責任・将軍は読む側** | 将軍が直接更新 | 将軍は**家老に「dashboard反映せよ」と依頼**。直接書かない |
| **Linear が正本・dashboard は高速サマリ** | dashboardを露出面として正本化 | 将軍の裏取り結果も**Linear正本＋dashboardサマリ**の既存構造に載せる |
| **ポーリング禁止（API節約）** | 定期巡回 | **イベント駆動のみ**（task-notification / 足軽の上申 / 殿の指示で起きる）。定時巡回しない |
| **指揮系統（将軍→家老→奉行/軍師→足軽）** | 将軍が足軽直接操作 | 平時は系統遵守。足軽直接操作は tmux故障等の非常時のみ（明示条件下） |

**帰結**: v0.3 の将軍は「自分でdashboardを書き、定期巡回し、足軽を直接叩く」のでなく、
**「イベントで起き、裏取りし、家老経由で反映させ、系統を通して指揮し、殿には既存の要対応で上げる」**。
既存統治の中で自律する。

## 設計原則（CODEX最小対案・D1〜D5反映）

```
原則1: 前進より封じ込め（v0.2継承）。
原則2: UI操作は「回数」でなく「適用条件」で縛る（D5）。
        安全に観測可能な特定状態（例:入力欄に残った/clearの宙吊り）にだけ解除許可。
        文脈破壊しうる状態は解除せず殿へ。
原則3: 「実装完了」と「要求達成」を分ける（D2）。
        実装完了=A+B（実体+git）。要求達成=別起源の確認（テスト実行・仕様突合）を追加要件。
        将軍は「実装完了」までを自律判定し、「要求達成」は別起源確認まで保留。
原則4: dashboardは家老経由（統治整合）。将軍は不確実性を家老に伝え家老が反映。
原則5: 異常「対応」ループと異常「発見」ループを分ける（D1）。
        対応=怪しい対象だけ。発見=印非依存の安価な劣化検知を別に残す（下記）。
原則6: 監視が苦しいほど縮退（v0.2継承・ただしポーリング禁止と両立）。
```

## 異常「発見」ループ（D1対処・ポーリング禁止と両立）

「怪しい印だけ見る」と印が付く前の沈黙を見落とす（CODEX D1）。だがポーリングは禁止。
両立させる = **定期巡回でなく、イベントの"不在"を検知する安価な仕組み**：

```
発見は「能動巡回」でなく「受動シグナル＋期限」で行う：
  - 各工程に「次の上申が来るべき期限」を持たせる（例: 着手通知から N 分）
  - 期限までに上申イベントが来なければ、それ自体をイベントとして将軍が1回だけ起きる
    （ScheduleWakeup を「期限アラーム」として使う。定期巡回でなく1回の目覚まし）
  - 起きたら該当対象だけ裏取り（全ペイン見ない）
→ これは「ポーリング（無条件反復）」でなく「期限切れ（条件付き単発）」ゆえ掟に反しない
```

真実源の優先順位（v0.2継承・実体>git>Task>tmux表示>自己申告）。

## 完了判定 二層化（D2対処）

```
【実装完了】= 系統A（実体：期待ファイル存在＋中身が仕様・空/TODO不可）
            ＋ 系統B（履歴：commit済・正ブランチ・意図した差分）
  → 将軍が自律判定。次工程展開はここで可（ただし可逆な範囲）。

【要求達成】= 実装完了 ＋ 系統D（別起源：テスト実行結果・仕様突合・レビュー）
  → 作者生成物と独立な確認。将軍レビュー or CI。ここまでで「本当に完了」。
  → 要求達成前は dashboard に「実装済・未検証」印（家老経由）。
```

## 自律ループ v0.3（イベント駆動・統治遵守）

```
【起床契機】（定期巡回でなくイベント）
  - task-notification（背景処理完了）
  - 足軽/軍師/奉行の上申
  - 殿の指示
  - 期限アラーム（上申が来ない工程の期限切れ・上記発見ループ）

【1起床でやること】
  1. 起こした対象だけ真実源優先で裏取り（全ペイン見ない・原則5）
  2. 分類：
     ├ 封じ込め対象（暴走兆候）→ 次工程展開を保留・家老に「隔離」共有依頼
     ├ 実装完了（A+B一致）→ 可逆な次工程を系統経由で展開（家老→軍師/奉行→足軽）
     ├ 要求達成前（A+Bのみ）→ 別起源確認（将軍レビュー/CI）へ
     ├ 単純詰まり（レート制限＝待つ / UI宙吊り＝原則2の適用条件下のみ解除）
     └ 判断要 → 可逆なら自律・不可逆は殿へ
  3. 家老に dashboard 反映を依頼（将軍は直接書かない・統治整合）
  4. 殿へ上げる（下記トリガー）→ 家老経由で dashboard「要対応」に集約
  5. 未解決異常の期限アラームを1回予約 / 無ければ何も予約しない（負荷ゼロ）
```

## 殿へ上げるトリガー（家老経由・dashboard要対応へ）

```
- 自律復旧2回失敗 → 止めて殿へ
- 完了判定が系統間で矛盾（表示done・実体なし等）
- 不可逆・外向き（push/マージ/削除/外部送信/課金）
- 一定時間どの工程も前進なし（期限アラームで検知）
- 将軍逼迫（下記フェイルセーフ）
```

## 将軍フェイルセーフ（D3対処・自己申告から切り離す）

CODEX D3：将軍の健康を将軍自身の書き込みに頼るのは単一障害点対策にならない。
→ **健康監視の真実源を将軍の外に置く**：

```
- 将軍は起床のたび status/shogun_heartbeat.yaml に最終起床時刻＋世代を書く（生存の足跡）。
- ただし「将軍が止まった」判定は将軍でなく【家老】が持つ：
    家老は自分の作業のついでに heartbeat 鮮度を確認し、
    一定時間 stale なら家老が dashboard「要対応」に「将軍停止疑い」を上げる。
- dashboard を健康監視の"真実源"にしない。真実源は heartbeat ファイル実体。
  dashboard は家老が反映する露出面にとどめる。
→ 将軍が落ちても、家老という別主体が気づいて殿に露出する。自己申告依存を断つ。
```

（将来: heartbeat 鮮度監視を cron/別プロセスに移せばさらに堅い。今は家老が担う）

## 副作用の世代制御（D4対処）

CODEX D4：世代番号を「結果の破棄」でなく「副作用を打つ権利」に使う。

```
- 各起床に世代番号を付す。
- read（裏取り）は自由。だが write系副作用（隔離・notify・次工程展開・家老への反映依頼）は
  「現世代が最新である」ことを打つ直前に確認してからのみ実行。
- 古い世代の起床が後から副作用を打とうとしたら、その時点で最新世代でなければ破棄。
  → read と write を分け、write だけ世代ゲートを通す。
```

## 境界線（殿確定・不変）

- **将軍 自律**: 封じ込め・裏取り・実装完了判定・可逆な次工程展開（系統経由）・家老へのdashboard反映依頼・可逆判断
- **殿のみ**: 不可逆・外向き（push/マージ/削除/外部送信/課金）＋自律2回失敗の判断

## 残る未解決論点（v0.4 or 実装時）

- 「怪しい」「封じ込め副作用の具体（保留のみか/pane操作停止まで含むか）」の観測可能な定義
- 系統Aの「仕様を満たす」の仕様源（仕様が古い/分散/曖昧な時の真）
- 系統D（要求達成の別起源確認）をどこまで自動化するか（CIの有無）
- 期限アラームの適切な期限値（工程種別ごと）
- heartbeat 鮮度監視を家老が確実に担えるか（家老も詰まる実績あり→将来cron化）
