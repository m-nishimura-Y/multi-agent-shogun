## 4. MCP ツールの使い方（遅延ロード）

Linear MCP ツールは遅延ロード方式。使用前に必ず `ToolSearch` で検索せよ。

```
1. ToolSearch で "linear" or "select:mcp__claude_ai_Linear__save_issue" を検索
2. 返ってきたツール（mcp__claude_ai_Linear__xxx）を使用
```

### よく使うツール
| 操作 | ツール |
|------|--------|
| Issue 一覧 | `mcp__claude_ai_Linear__list_issues` |
| Issue 作成/更新 | `mcp__claude_ai_Linear__save_issue`（id 無し=作成、id 有り=更新）|
| Issue 詳細 | `mcp__claude_ai_Linear__get_issue` |
| コメント追加 | `mcp__claude_ai_Linear__save_comment` |
| プロジェクト作成/更新 | `mcp__claude_ai_Linear__save_project` |
| マイルストーン作成/更新 | `mcp__claude_ai_Linear__save_milestone` |
| ラベル作成 | `mcp__claude_ai_Linear__create_issue_label` |

### save_issue の必須/推奨フィールド
- `title`（必須）/ `team`: "nishimura_task"（作成時必須）
- `project`: "YUI番（入社台帳PoC）" 等
- `labels`: 自分の役職ラベルを必ず（例: `["軍師"]`）
- `priority`: 0=None 1=Urgent 2=High 3=Medium 4=Low
- `state`: "Backlog" / "Todo" / "In Progress" / "In Review" / "Done"
- `milestone`: 該当マイルストーン名
- `description`: Markdown。**改行はエスケープせず実際の改行を使う**（`\n` と書かない）

## 5. 運用フロー

### タスク起票のタイミング
- 将軍から新しい cmd が来て、複数ステップに分解されるとき → 親 Issue + 子 Issue
- 殿判断が必要な論点が出たとき → ISSUE として起票し `priority` を上げる
- 設計レビュー（CODEX）で残論点が出たとき → 軍師が起票

### ステータス遷移
```
Backlog（未着手・温め） → Todo（着手予定） → In Progress（作業中）
  → In Review（家老/将軍の検証待ち） → Done（完了）
```

### 🚨 調査・作業が終わったら Issue コメントに結果を残せ（必須）

```
████████████████████████████████████████████████████████████████
█  調査・作業の完了報告は Issue の「コメント」に書く            █
█  → 殿が Linear だけ見れば経緯を追える                        █
████████████████████████████████████████████████████████████████
```

- **調査・作業が完了したら、その Issue に `save_comment` で結果サマリを残す**
- **コメント冒頭に必ず「役職」と「コマンド番号 cmd_XXX」を明記**（必須）
  - 例: `【軍師・cmd_323】Phase1 簡素化完了。22接続→最大6接続…`
  - 例: `【家老・cmd_321】M1 を Linear に反映完了…`
  - **理由（殿の指示）**: Linear だけ見れば、その作業がどの cmd でなされたか追える。
    cmd と Issue の対応が将軍の手元 YAML にしか無い状態を解消する。
  - 1つの Issue に複数 cmd が紐づく場合は、コメントごとに該当 cmd を書けば時系列で追える
- コメントに書く内容: 何を調べたか / 結論 / 残課題（殿確認が要る点）/ 出典
- **長大な調査結果は description に、完了報告サマリはコメントに** という使い分けでもよい
- ステータスを In Review / Done に動かすときは、必ず対応するコメントを添える（無言で状態だけ変えるな）
- これにより「いつ・誰が・どの cmd で・何を終わらせたか」が Issue のタイムラインに残る

### dashboard.md との役割分担（v1.2.0 で再定義）

```
████████████████████████████████████████████████████████████████
█  Linear = タスク/プロジェクト/ISSUE の正本（構造的に追う）  █
█  dashboard.md = 殿との対話面（サマリ・相談・所見）          █
████████████████████████████████████████████████████████████████
```

**dashboard.md に書くもの（4つだけ）**:
1. 🎯 **今ここ** — 現フェーズ・マイルストーンを 1〜2 行
2. 🚨 **殿に相談・判断してほしいこと** — サマリのみ。詳細は「→ NIS-X」で Linear へ誘導
3. 💬 **将軍からの所見・提案** — Linear に書きにくい対話・思考・提案
4. 📊 **ざっくり戦況** — 全軍が今何をしているか 3〜4 行

**dashboard.md に書かないもの（Linear に任せる）**:
- ❌ 個別タスクの一覧・ステータス（→ Linear）
- ❌ ISSUE の詳細本文（→ Linear。dashboard はサマリと NIS 番号だけ）
- ❌ 完了済みタスクの履歴（→ Linear）

**狙い**: 殿が朝イチで dashboard を開けば「今の状況」と「決めてほしいこと」が一目で分かる。詳細を追いたくなったら Linear へ飛ぶ。二重管理を解消する。

### 殿への可視化
- 殿判断が必要な Issue は `priority` を High 以上にし、`state` を Todo に
- 殿は Linear 上で直接判断・コメントできる

## 5.5 GitHub 連携（v1.1.0〜）

```
████████████████████████████████████████████████████████████████
█  PR を切るときは Linear Issue を必ず紐付けよ                 █
█  → PR の状態遷移で Issue が自動で動く（手動更新が消える）    █
████████████████████████████████████████████████████████████████
```

**連携状況**: yuidea 組織が Linear に接続済み。yui-ban を含む組織リポの PR が Linear から見える。

### PR と Issue を紐付ける3つの方法（どれか1つでよい）

| 方法 | やり方 | 効果 |
|------|--------|------|
| **マジックワード** | PR 説明に `Fixes NIS-6` 等 | マージで Issue が自動 Done |
| **非クローズ参照** | PR 説明に `Part of NIS-6` `Related to NIS-6` 等 | 紐付くが自動クローズはしない |
| **ブランチ名** | Linear の「Copy git branch name」で出る名前でブランチを切る | 自動リンク |

### マジックワード一覧
- **クローズ系**（マージで Issue を Done に）: `close` `closes` `fix` `fixes` `fixed` `resolve` `resolves` `complete` `completes` `implement` `implements`
- **非クローズ系**（紐付けのみ・状態は自動で閉じない）: `ref` `references` `part of` `related to` `contributes to` `towards`
- 複数紐付け: `Fixes NIS-6, NIS-7`

### 実装フェーズ（M2〜）の標準フロー
```
1. 着手する Issue を決める（例: NIS-6）
2. ブランチを切る（Linear のブランチ名 or 任意。命名に nis-6 を含めると確実）
3. 作業 → PR 作成。PR 説明の冒頭に紐付け文を書く:
     例) "Part of NIS-6" （実装計画書はまだ閉じないので非クローズ系）
     例) "Fixes NIS-12" （その Issue を閉じてよい単発作業なら）
4. PR が draft→open→merged と動くと Issue が自動で In Progress→In Review→Done
```

### 注意
- **マジックワードは PR の「タイトル or 説明」に書く**。コミットメッセージやコメントでは効かない
- yui-ban は今まで main 直 push だったが、**実装フェーズでは PR を立てて Issue と紐付ける**運用に移行
- main 直 push 禁止・PR マージは殿が行う（既存ルール踏襲。我らは PR 作成まで）
