# 報告書マニュアル

## 別働隊報告の読み方（digest 契約・必須 2026-07-13）

```
████████████████████████████████████████████████████████████████
█  別働隊報告は、既定で digest ブロックだけを読め。            █
█  body（result 以降）を全文 Read するな。                    █
████████████████████████████████████████████████████████████████
```

足軽の報告書（`queue/reports/ashigaru{N}_report.yaml`）先頭には
`digest:`（12行以内の要約）が必須化されている。集約役はこう読め：

1. **まず digest だけ Read**（`Read(limit=…)` で先頭のみ）。verdict / files /
   commit / blockers / skill_candidate / assumptions を掴む。
2. **body（result 以降）を全文読むのは、digest が旗を立てた時だけ**：
   - `blockers` が空でない → その足軽の body を部分 Read して詳細把握
   - `skill_candidate.found: true` → 評価に必要な箇所だけ Read
   - verdict が failed/blocked → 原因を body で確認
3. 旗が立っていない done 報告は、digest だけで集約に足る。全文 Read は
   コンテキスト浪費（API負荷・逼迫の主因）。

**なぜ**: 別働隊4名の報告を全文読むと、集約役のコンテキストが4名分で肥大し、
逼迫・停止して全体の律速になる。digest 契約で1報告あたりの費を頭打ちにする。

---

## 基本形式

```yaml
# queue/reports/gunshi_report.yaml
report_type: analysis | strategy | skill_evaluation | secretary
timestamp: "YYYY-MM-DDTHH:MM:SS"  # date コマンドで取得
task_id: gunshi_task_XXX
summary: "一行で要約"

# 内容（report_type による）

dashboard_draft: |
  ## セクション
  - 内容

awaiting: karo_review
```

---

## タイムスタンプ取得

```bash
date "+%Y-%m-%dT%H:%M:%S"
```

**自分で推測するな。必ずコマンドで取得せよ。**

## 報告タイプ別

### analysis（分析報告）

```yaml
report_type: analysis
analysis:
  findings:
    - "発見事項1"
    - "発見事項2"
  options:
    - option: A
      description: "説明"
      pros: ["利点"]
      cons: ["欠点"]
  recommendation: "推奨案"
  reason: "理由"
risk_assessment:
  level: low | medium | high
  details: "詳細"
  mitigation: "対策"
```

### skill_evaluation（スキル評価）

```yaml
report_type: skill_evaluation
skill_evaluations:
  - name: "スキル名"
    score: 16
    max_score: 20
    recommendation: approved | rejected | conditional
    reason: "理由"
    design_doc: "skills/designs/xxx.md"
```

### secretary（秘書業務）

```yaml
report_type: secretary
aggregated_reports:
  - ashigaru5: "タスクA完了"
  - ashigaru6: "タスクB完了"
```

## サマリ報告（足軽報告集約）

```yaml
# queue/reports/gunshi_summary.yaml
report_type: ashigaru_summary
timestamp: "YYYY-MM-DDTHH:MM:SS"
cmd_id: cmd_XXX  # 必須！
summary: "足軽N名の報告を集約"

reports:
  - ashigaru: 5
    status: done
    summary: "タスクA完了"
    skill_candidate: null
    reflection: null  # または {insight: "...", concern: "...", suggestion: "..."}
  - ashigaru: 6
    status: done
    summary: "タスクB完了"
    skill_candidate:
      name: "xxx-analyzer"
      evaluation: "16/20 推奨"
    reflection:
      insight: "キャッシュ戦略が有効だった"
      concern: null
      suggestion: "共通化検討"

# reflection 集約（v1.6.5追加）
# 足軽のreflectionに記載があれば、ピックアップしてまとめる
reflection_summary:
  notable_insights: []  # 組織で共有すべき気づき
  common_concerns: []   # 複数足軽で共通の懸念
  actionable_suggestions: []  # 実行可能な改善提案

# ============================================================
# Obsidian登録判定（v1.6.5追加）
# ============================================================
obsidian_worthy: true  # または false
obsidian_category: "知見/成功事例"  # 登録先カテゴリ
obsidian_title: "cmd_XXX: タスク名"  # ノートタイトル
obsidian_summary: "一行で概要"  # frontmatter用

dashboard_draft: |
  ## 進捗
  | 足軽 | ステータス | 概要 |
  |------|----------|------|
  | ashigaru5 | ✅完了 | タスクA完了 |

awaiting: karo_review
```

## Obsidian登録判定基準（v1.6.5追加）

### 登録すべきもの（obsidian_worthy: true）

| カテゴリ | 例 |
|----------|-----|
| 知見/失敗と学び | 問題の根本原因と再発防止策 |
| 知見/成功事例 | 横展開可能なベストプラクティス |
| 知見/未来設計 | アイデア、改善提案 |
| 案件/xxx | 重要な意思決定の経緯 |
| スキル | 新しいスキル作成 |

### 登録不要（obsidian_worthy: false）

- 単純な整理タスク（dashboard更新など）
- ルーティン作業
- 既存Issueへのコメント追記のみ

### カテゴリ例

```yaml
obsidian_category: "知見/失敗と学び"
obsidian_category: "知見/成功事例"
obsidian_category: "知見/未来設計"
obsidian_category: "案件/ipadress-manager"
obsidian_category: "スキル"
```

## 報告完了の手順

1. 報告書を書く
2. **永続化する**（サマリの場合）
3. **notify.sh で家老に通知する**

通知を忘れると任務未完了扱い。
